# 样本批次导入 — 验证报告

日期：2026-11-17 · 环境：本地 MySQL 8.0.40（端口 17741）/ Redis 7.2.6（16379）/ uvicorn（19241）/ worker，均为真实进程。

## 脚本
- `verify_batches.py` — 端到端验证（47 项断言，可重复执行，开头自动清理上一轮状态）。连续两轮全部通过。
- `frontend_smoke.mjs` — Node DOM 桩渲染全部五个页面，校验批次信息展示。
- `verify_output.txt` — 最近一次完整输出。

## 覆盖与结果（47/47 通过）
- **鉴权**：未登录 401；viewer 导入 403。
- **整批导入与原子替换**：导入 200 行批次后 current 切换、种子批次退役且 `telemetry` 表受保护不删；批次表行数精确。
- **幂等重试**：同批同内容返回 `replayed=true`，表行数不变、批次记录唯一、不重复生效。
- **同批异内容**：返回 409，生效批次不被污染。
- **坏行**：第 202 行非法时间 → 422，批次留痕 `failed` 与原因，旧版保留，未建数据表。
- **重复记录**：(sensor_id, recorded_at) 重复 → 422，旧版保留。
- **排队试验跨批执行**：侧连接持有试验锁模拟长试验 → 创建试验绑定 `verify-b1`（排队）→ 导入 `verify-b2` 0.1s 完成（换批不等待长试验）→ 释放锁后试验对原批次表执行，结果注明 `verify-b1`、行数 40 与原批次数据一致。
- **引用释放前不清理**：试验占用期间旧批次为 `retired` 且表存在；试验完成落终态后清理为 `cleaned` 并删表。
- **前后查询与写探针隔离**：EXPLAIN 的 `table` 列、结果行数（75）均来自所绑定批次表；写探针只消耗绑定批次表的 auto_increment（301→321），种子表保持 5001。
- **结果注明批次**：结果 JSON 与导出文件均含批次号与内容哈希。
- **导入中断恢复**：100,000 行导入中对 uvicorn 发 SIGKILL（落点 during-load，装载事务中途），批次停留 `importing`；重启后同内容重试恢复并生效，表行数精确 100,000、记录唯一；再次重试幂等，异内容仍 409。
- **并发同内容重试**：两并发请求均 200，恰好一次生效一次幂等，记录唯一。
